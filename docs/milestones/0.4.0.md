# Milestone 0.4.0 — Connected bibliographies and source maintenance

**Planned. No implementation, preview or release claimed.** The maintainer assigned this logically separate scope on 20 November 2026. Current released metadata remains 0.2.0 and reviewed-import development targets 0.3.0.

## Agreed scope

- Ingest bibliography-manager interchange files, initially BibTeX, RIS and CSL-JSON.
- Explore explicit, read-only connections to Zotero and other managers for selected items or collections.
- Preserve identifiers, provenance, edition distinctions and local edits; review proposed reimport changes rather than replacing records silently.
- Review broken or stale source links, keeping failed checks distinct from evidence that a work is unavailable.
- Improve sourced correction, retraction and expression-of-concern notices. Verify that the notice applies to the cited work and retain the original citation and editorial decision.
- Reuse the reviewed-import records and decision model instead of creating a second identity system.

Embedded Zotero metadata encountered during article extraction remains a 0.3.0 preservation concern. External collections, manager services and ongoing source upkeep belong here.

## Developer learning and live demos

The maintainer also requested this track on 20 November 2026. Plan a public learning site with a live browser playground, progressive tutorials and heavily annotated examples. Do not limit documentation to an API inventory.

- Start with a minimal page, then explain initialization, notation, formatting styles, CSS/namespaces, panel behavior and accessibility.
- Cover structured records, editions/year letters, access preferences, artwork, evidence, tags, shared bibliographies, editor notes and reviewed import. Each example should connect visible output, source notation and configuration.
- Provide editable examples with reset controls, complete source and downloadable runnable projects for npm and non-npm users.
- Explain unsuccessful cases too: unknown references, ambiguous matches, skipped extraction regions, stale revisions, unavailable providers and offline behavior.
- Include integration recipes for static sites and build pipelines, then a worked draft.inator integration showing explicit review, revision checks and host-owned persistence. The host editor remains a separate project. Initial read-only inspection and compatibility questions are recorded in [the integration boundary](../draft-integration.md).
- Maintain a feature-to-example/documentation matrix so additions cannot quietly lose coverage. Distinguish supported APIs from experiments and identify the library version used by each example.

GitHub Pages can host the static HTML/CSS/JavaScript learning site; see [GitHub's hosting documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). Build from the repository using an intentional deployment workflow with correct project-base paths. No deployment is claimed here. Local parsing/compiling and saved provider fixtures should make the main demonstrations usable without a backend or credentials. Live provider lookup is optional and subject to browser CORS/provider constraints; server-side checks, credentials or proxies require separately hosted services. A published demo must never include private manuscripts.

## Acceptance and evidence

No candidate or verification run yet. Developer acceptance should include completing the starter tutorial from a clean download, running every example, verifying the deployed project-base paths, keyboard/narrow-screen behavior, offline fallback and draft.inator revision-conflict handling. Before implementation, define fixtures for format/edition fidelity, reimport conflicts, unavailable services, link-check false negatives and notice-to-work identity. Follow the repository check-in procedure and independent milestone reviews before release.

## Known limits and follow-up

Provider priorities and exact connector contracts remain to be chosen from adopter needs. Remote access must be explicit; local-file workflows should remain usable without service credentials or AI. More access providers, version-specific research artifacts and claim-to-source relationships remain broader roadmap items rather than automatic additions to this milestone.
